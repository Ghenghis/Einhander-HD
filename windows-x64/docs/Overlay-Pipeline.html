Overlay Pipeline

RAM-streamed code capture and native shards · ← index

Why Overlays Matter Here

Einhänder streams code into RAM at runtime — modules the static analyzer cannot see in the boot EXE. Until those regions are captured during play and compiled as native shards, E2E coverage is impossible by definition.

Capture Store

build-release\overlay_captures.json — additive store, appended across sessions.

build-release\overlay_captures.json.d\ — per-capture history dir (~3 MB).

Boot log confirms wiring: additive overlay capture store = ...overlay_captures.json (+ .d history)

Current contents: one record — load_addr 0x8001D000, size 4,100 bytes, small executed-PC set, empty function_entry_pcs. This is a seed, not coverage.

Record Shape

{
  "load_addr": "0x8001D000",
  "size": 4100,
  "executed_pcs": [...],       // PCs actually run inside the region
  "function_entry_pcs": [...]  // proven function entries (empty so far)
}

Runtime Guard Relevant to Overlays

The runtime logs overlay_region_floor = 0x32000 (game text end), text_image_lo = 0x10000 and arms a text image guard (0x80010000..0x80032000) — the resident image is protected; anything loaded above the floor is capture-eligible.

Path to Native Shards

  1. Capture growth — real play-through sessions. Each session appends overlay records; coverage is measured by distinct load_addr regions and executed-PC density inside them.
  2. Shard compilation — captured regions become native shards alongside generated\ output (see psxrecomp\tools\aot_overlay_spike\README.md for the spike design).
  3. Loop — as shards compile, more code executes natively, which surfaces further overlay loads.
