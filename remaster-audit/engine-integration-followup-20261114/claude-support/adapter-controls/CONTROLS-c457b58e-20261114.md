## New observations (source reading only; none blocks)
- **N1 (low): a failed peer lookup keeps only a short error string.**
  - Root asked for failure evidence to be retained.
  - When `select_owned_tcp_peer` rejects, `row['peer']` is never set and the message has no details.
    `'...belongs to another process'` gives neither the pid seen nor the match count.
  - Suggestion: put the match summary in the raised message, or in `row['peer_lookup']` before `_require`. For
    example `matches=[{pid, status}]` and `count`. Keep it bounded (a 4-tuple filter gives at most a few rows).
- **N2 (low): peer-lookup time is not recorded.**
  - `psutil.net_connections` is a blocking system-wide call. The deadline is enforced afterwards by `left > 0`, which
    matches the documented acceptance-deadline pattern of `_listener`.
  - Suggestion: add `row['peer']['elapsed_s']`, as `_listener` already records `elapsed_s`.
- **N3 (note): the guard does not re-check the peer offline.**
  - `validate_active_adapter` gets the listener identity brackets but not `row['peer']`.
  - A later consumer re-validating a receipt with the pure guard alone therefore cannot confirm the peer binding;
    today that rests on the collector having raised.
  - Optional future guard revision (a new guard hash, so root's call): for both samples require `peer.pid ==
    expected_process[0]`, `peer.identity == expected_process`, `peer.server == ['127.0.0.1', port]` and `peer.status
    == 'ESTABLISHED'`.
- **N4 (note): `decode_present_reply` does not raise a single exception type.**
  - `AdapterEvidenceError` covers bound, constant, float, duplicate and ID failures.
  - `UnicodeDecodeError`, `JSONDecodeError` and the int-digit `ValueError` are all ValueError, as is
    AdapterEvidenceError.
  - Deep nesting within 16 KiB (`[`×8192) may instead raise `RecursionError`, which is not a ValueError. Whether it
    does depends on the 3.14 stack-based limit.
  - `sample()` catches `Exception`, so the collector still fails closed. Only a direct caller catching ValueError
    would miss it.
  - Optional: wrap `json.loads` in `except (ValueError, RecursionError)` and re-raise as AdapterEvidenceError.
- **N5 (caller note, alongside root's `allow_nan=False`): lone surrogate escapes are accepted.**
  - Python's json maps `"\ud800"` to a lone-surrogate str.
  - The default `json.dumps(ensure_ascii=True)` is safe.
  - A receipt writer using `ensure_ascii=False` and UTF-8 would raise `UnicodeEncodeError` and could lose the receipt.
    The same applies to duplicate-key error messages that quote the key.
  - Requirement for future writers: `allow_nan=False` and keep `ensure_ascii=True`.
- **N6 (note): big integers in unvalidated fields.**
  - Up to the default `int_max_str_digits` (4300 under `-I`), a big integer is accepted in fields the guard does not
    validate. The JSON stays valid; validated fields stay bounded by `_integer < 2**64`.
  - No action needed.
- **N7 (low, documented limitation): (dev, ino) detects replacement, not in-place rewriting.**
  - It does not detect truncation or rewriting of the same file, which control S6 records as expected behaviour.
    Content is left to the guard.
  - If wanted: record size and prefix hash at construction, then require append-only growth at `finish`.
- **N8 (unverified platform assumption; fail-closed): when the server row appears.**
  - The peer check assumes Windows lists the server-side ESTABLISHED row with the listener owner's PID as soon as
    `connect` returns, including while the connection is still in the accept backlog.
  - I believe this is true for `GetExtendedTcpTable` but have NOT verified it.
  - If it is false, a sample fails as "missing" with no retry: fail-closed, not unsafe, but it could cost a real
    attempt. A first authorized run should record the peer row status and timing.
